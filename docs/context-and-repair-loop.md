# 上下文组装与受限修复闭环

ResolveX 不把“反思”实现成一段让模型自由发挥的提示词。当前闭环由确定性代码控制：上下文
先按可信度和预算组装，工具执行后验证真实业务结果，失败再按统一分类决定停止或重新规划。

## ContextAssembler v2

ContextAssembler 为每类信息记录来源、可信级别、优先级、原始条目数、实际保留条目数和估算
Token 数。估算采用与供应商无关的确定性算法，因此适合本地测试和不同模型之间的稳定比较，
但不冒充供应商账单中的精确 Token 数。

系统安全规则、MySQL 当前业务状态和可用工具契约是必需上下文。预算不足时依次移除语义记忆、
最早的历史消息、低相关政策片段和对话摘要；当前请求至少保留一条。如果必需上下文本身已经
超过预算，组装过程直接失败，不会静默删除授权或业务事实。

主要配置：

- `CONTEXT_MESSAGE_LIMIT`：进入候选集的最近消息上限；
- `CONTEXT_MAX_ESTIMATED_TOKENS`：最终上下文的估算 Token 上限。

## Failure Attribution Core

失败记录使用统一结构，至少包含阶段、类别、原因、工具、错误码、是否可修复、修复动作和尝试
次数。当前覆盖规划、政策、工具执行和结果验证阶段。结构化记录保存在 Agent 状态中，并通过
结构化日志写入现有 OpenTelemetry 链路，不另建日志平台。

主要失败类别包括：

- 无效规划；
- 政策或权限拒绝；
- 非法工具参数；
- 外部依赖不可用；
- 工具执行失败；
- 业务结果验证不一致。

## Verify → Diagnose → Repair → Replan

```text
Execute Tool
    ↓
Verify business outcome
    ↓
Diagnose structured failure
    ├─ STOP ───────────────→ controlled response
    └─ REPLAN → policy check → execute → verify
```

只有只读工具的临时依赖故障和验证不一致可以进入重新规划，默认最多一次。退款、取消订单等写
操作不会因为验证失败而自动再执行；政策拒绝、越权访问和非法参数也不能通过重新规划绕过。
每次重新规划仍需重新经过工具白名单和政策检查，并生成新的工具调用 ID。

`MAX_AGENT_REPAIR_ATTEMPTS` 控制单次 AgentRun 的修复次数，范围为 0～3，默认 1。工作流仍受
`MAX_AGENT_STEPS` 总步数限制，形成双重预算。

## 当前边界

本阶段只实现闭环所需的上下文治理、失败语义和安全修复。不包含多智能体讨论、无限自主规划、
树搜索、独立数据仓库或新的分析大屏。离线 Case Analysis 可以在这些结构化证据稳定后另行实现。
